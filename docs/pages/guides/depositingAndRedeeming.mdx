# Depositing and redeeming

A deposit is two transactions. A redeem is one. Both create a query on the conduit, and both are
built for the account that sends them.

## Deposit

1. **Approve the conduit** for `amount` of the asset. A plain ERC-20 call; the deposit spends the
   allowance. On a wallet that supports EIP-5792, [`toCall`](/utilities/toCall) batches the pair
   into one confirmation.
2. **Build the call** with [`buildDepositConduitCall`](/actions/buildDepositConduitCall), or let
   [`getDepositConduitCall`](/actions/getDepositConduitCall) read the vehicle for you and hand back
   the query id.
3. **Simulate, then send.** `simulateContract` returns the revert before the user signs. From
   React, see [Sending from React](/guides/sendingFromReact).

## Redeem

[`buildRedeemConduitCall`](/actions/buildRedeemConduitCall) burns shares the conduit already holds
for the account. No approval. [`getRedeemConduitCall`](/actions/getRedeemConduitCall) reads the
output asset for you.

## The sender

`conduit.create()` binds the query salt to `msg.sender`, requiring `query.salt` to equal
`keccak256(abi.encode(msg.sender, salt))`. The call is encoded for one sender and reverts
`InvalidQuerySalt` from any other. Through a Safe, an EIP-5792 batch or a relayer, `msg.sender`
is that contract. Build the call for it and set `receiver` to the user.

## The salt

The salt is the operation's identity. Generate it once with [`randomSalt`](/utilities/randomSalt)
when the user starts the operation, and hold it across simulation, signature and retry. A retry
with a fresh salt is a second query. [`toQueryId`](/utilities/queryIdentity#toqueryid) turns the
built query into the id an indexer holds.

## Slippage

On a deposit, `minOutput` is a floor on the vehicle's output, in vehicle shares. Derive it from
[`estimateVehicle`](/actions/estimateVehicle) and
[`applySlippage`](/actions/estimateVehicle#applyslippage). [`estimateConduit`](/actions/estimateConduit) prices the same deposit in
conduit shares, a different denomination; a floor taken from it is wrong in one direction or the
other. Fees and the share rate sit between the vehicle's output and the conduit shares the user
receives, so the floor is not a minimum received.

On a redeem, `outputAsset.value` is a floor on the vehicle's asset output, before the conduit's
fees. Derive it from [`estimateConduit`](/actions/estimateConduit) in `QueryMode.REDEEM`, which is
net of those fees.

```ts
const estimate = await estimateConduit(client, {
  conduit,
  asset: { asset: conduit, value: shares },
  mode: QueryMode.REDEEM,
  estimationType: EstimationType.OUTPUT,
})

const call = buildRedeemConduitCall({
  conduit,
  shares,
  sender,
  outputAsset: { asset: estimate.asset, value: applySlippage(estimate.value, 50) },
  salt,
})
```

The floor is checked at creation only. A redeem that queues settles later at the fulfillment rate,
which can fall below it.

## After the transaction

On a synchronous vehicle the query settles in the same transaction. On an async vehicle it stays
short of settlement until [`buildProcessConduitQueryCall`](/actions/buildProcessConduitQueryCall)
advances it, sent by the query's receiver or by a holder of `CONDUIT_PROCESS`.

[`extractQueries`](/utilities/receiptHelpers#extractqueries) reads each query's struct and vehicle
out of the receipt. A redeem's struct is not known before the transaction, and both
[`getQueryState`](/actions/getQueryState) and `buildProcessConduitQueryCall` take it, so store it.

```ts
const [{ query, vehicle }] = extractQueries(receipt, conduit, chainId)

const state = await getQueryState(publicClient, { vehicle, query })
if (state === QueryState.PAUSED || state === QueryState.UNLOCKING) {
  const call = buildProcessConduitQueryCall({ conduit, query })
}
```
