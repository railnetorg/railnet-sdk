# Query identity

Every conduit operation creates a query, and the protocol gives it two identifiers. Both are
derivable off chain, so a UI or an indexer can follow an operation from the moment it is built.

## toQuerySalt

```ts
import { toQuerySalt } from '@railnetorg/railnet-sdk'

const querySalt = toQuerySalt({ sender: account.address, salt: randomSalt() })
```

`keccak256(abi.encode(sender, salt))`, the value `conduit.create()` requires in `query.salt` and the
one `createRedeemFromConduitShares()` derives itself. A call built for one sender reverts
`InvalidQuerySalt` when another sends it. The builders call it; it is needed directly only to
recognise a query built elsewhere.

## toQueryId

```ts
import { toQueryId } from '@railnetorg/railnet-sdk'
import { mainnet } from 'viem/chains'

const queryId = toQueryId({ chainId: mainnet.id, vehicle, query })
```

`keccak256(abi.encode(chainId, vehicle, query))`, the id the conduit emits in `QueryCreated` and the
key an indexer holds. [`getDepositConduitCall`](/actions/getDepositConduitCall) returns it computed.

A deposit's id is known before the transaction is sent. A redeem's is read from the receipt with
[`extractQueryIds`](/utilities/receiptHelpers#extractqueryids). See [`getRedeemConduitCall`](/actions/getRedeemConduitCall#returns).

Keeping the salt across simulation, signature and retry is covered in [The salt](/guides/depositingAndRedeeming#the-salt).
